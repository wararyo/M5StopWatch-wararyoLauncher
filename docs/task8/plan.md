## 決めたこと（2026-09-23、ユーザーと合意）

### VBUSがある間はlight sleepを禁止する

MuteHidと同じ保守的な方針を採る。VBUSが4000mVを超えている間は `ESP_PM_NO_LIGHT_SLEEP` のロックを持ち、
電池駆動のときだけ自動light sleepを許す。MuteHidではUSB接続中のlight sleepでコンソールが落ち、
書き込みもできなくなった（MuteHidの省電力記録 4.5節）。本機でも書き込み経路を失う危険を避ける。

帰結として、**USB側の電流を下げられるのはDFSとポーリング削減だけ**になる。
MuteHidの240→80MHzで約8〜9mA減をそのまま当てはめても、画面OFFは27mA前後にとどまり、
**USB側20mAには届かない見込み**。達否は実測で判定し、未達なら残る消費を記録する（全体計画 作業8の完了条件）。
light sleepの効果は電池駆動の測定でだけ評価する。

### 電池駆動の測定は3回

1回に数時間から半日かかるため、次の3回に限る。

| 回 | 構成 | 比較で分かること |
|---|---|---|
| 1 | 240MHz固定（作業7の初版と同じ動作） | 基準 |
| 2 | DFS＋GPIO通知・期限待機（8-3・8-4の後） | USB側でも測れる施策の、電池側での効果 |
| 3 | ＋tickless idle・自動light sleep（8-5の後） | light sleepの効果（2との差） |

DFSとGPIO化を電池側で個別に分けない。両者の個別の差はUSB側で測る。

使い方は「画面OFFで放置」に固定する。操作を人手で再現する必要がなく、条件を揃えやすいため。
満充電・非充電中から始め、比較は同じ電圧帯（4.1→3.7V）の所要時間で行う。
停止まで放置できた回は、停止までの時間も記録する。

## 8-0. 電池電圧ロガー

### 目的

StopWatchの電源IC（M5PM1）は電圧しか読めず、電池側の電流は測れない。
そこで電池駆動の時間と電圧の推移を本体に記録させ、USBを挿し直した後に吸い出す。
MuteHidの `PowerProbe` の記録部分に倣う。

### 決めたこと

- **専用ビルド `m5stopwatch-drain` だけに入れる**。通常ビルドは測定の道具を持たない（作業7で固定した方針）。
  `m5stopwatch-measure` にも混ぜない。フレーム集計のシリアル出力が電池駆動中の負荷に加わるため。
- **開始にシリアルを使わない**。VBUSが消えたら自動で記録を始め、VBUSが戻ったら止める。
  シリアルを開くと +16mA が乗るので、開始操作のためにポートを開くこと自体が測定を汚す。
  新しい記録は前回分を消す。吸い出す前にUSBを抜き直さないこと。
- **UIは変えない**。吸い出しはシリアルの1文字コマンド `O` だけ。記録中の表示もない。
- 記録はRAMに1分ごと（最新24時間分）、NVSに15分ごと（最初の32時間分）。
  RAMは細かいがリセットで消える。NVSは電池が切れても残る。吸い出しはRAMにあればRAM、空ならNVSを出す。
- NVSは既定の `nvs` に専用名前空間 `launcher_drn` を作り、1項目を上書きし続ける。
  設定の `launcher` 名前空間とスキーマには触れない。15分ごとの1回書き込みなので、
  描画・毎秒計測でFlashへ書かない規約（全体計画8.3節）の対象にはならない。
- 各記録には経過秒・電池電圧・状態（画面点灯・充電中・USB給電）を残す。
  1分ごとのI2C読み出しと15分ごとのNVS書き込みが測定対象に加わるが、
  3回とも同じ条件なので比較は成り立つ。

### 手順

1. `pio run -e m5stopwatch-drain` を `install-host` で導入する。
2. 満充電・非充電中を確認する。書き込みでポートを開いているので、本体をリセットする。
3. USBを抜く。1分以内に記録が始まる。そのまま放置し、無操作消灯させる。
4. 3.6Vを下回るか停止するまで待つ。USBを挿し直し、
   `python tools/battery_drain.py COM11 docs/task8/<日付>-drain-<回>.csv` で吸い出す。
   電池が切れて再起動していた場合は、NVSの15分刻みの記録が出る。

`tools/battery_drain.py` はCSVの保存と、4.1→3.7Vなど電圧帯ごとの所要時間の表示を行う。
ポートはDTR/RTSを下げてから開き、本体をリセットしない（`capture_serial.py` と同じ扱い）。

2026-09-23に実装し、USBを抜いて3分間の記録（4件、NVSに1件）が取れることを実機で確認した。

## 8-2. CDCポートを開くと +16mA 乗る件

### 仮説

ポートを開く前は、Windowsがセレクティブサスペンドでバスを休止させている。
ポートを開くとバスが起き、閉じても休止へ戻らない。

根拠は次の3点。

- 作業7の測定で、USB充電器（データ接続なし）とPC接続・ポート未開封が同じ35.5mAだった。
- 上がるのはポートを開いたときだけで、ケーブルを挿しただけでは上がらない。
- 本体のリセットで戻る。リセットはUSBの再列挙を伴うので、ホスト側の状態もやり直しになる。

バスが動いている間、ESP32-S3はUSB PHYとBBPLL（`USB_SERIAL_JTAG_LL_PHY_DEPENDS_ON_BBPLL`）を動かし続ける。
+16mAはその費用だと考えている。

### 確かめ方

`usb_serial_jtag_is_connected()` は、ホストが1msごとに送るSOFが届いているかを返す
（IDFの `usb_serial_jtag_connection_monitor.c`）。バスが休止していればSOFは来ない。
そこで `m5stopwatch-measure` に、SOFの有無とVBUSの変化の履歴を残す `[UsbDiag]` を加えた。
UIは変えず、測定ビルドだけに入れる。

- 変化があったときだけ、時刻とSOF・VBUSを記録する（最大32件）。
- SOFが0→1になった2秒後に履歴をまとめて出す。ポートを開く前のことは開いた後でしか読めないため。

実機での手順（電池測定の後に行う）:

1. `m5stopwatch-measure` を導入し、**本体のボタンでリセット**する。PCに挿したままポートは開かない。
2. 1分以上置いて電流を読む（作業7では36.0mA）。
3. `capture_serial.py` を `reset` なしで開き、電流と `[UsbDiag]` の履歴を読む。
4. ポートを閉じて電流を読む。次にリセットせずにケーブルを抜き差しし（電池で動き続ける）、もう一度読む。

### 判定

| 履歴 | 解釈 | 対応 |
|---|---|---|
| 起動後 `sof=0` が続き、開いた時に `sof=1` | 仮説どおり。ホストのサスペンドの有無の差 | 本体の不具合ではない。実使用の充電器給電では起きない。測定手順の注意として残す |
| 開く前から `sof=1` | 仮説は外れ。ポートを開いたことで本体側の何かが変わる | コンソール出力の流れ方・USJの状態を追加で調べる |

4.の抜き差しで戻れば、「閉じても戻らない」はホストがバスを起こしたままにするため、と確定する。

8-5への影響: IDFの `CONFIG_USJ_NO_AUTO_LS_ON_CONNECTION` はSOFの有無でsleepを禁止する。
仮説どおりなら、ポート未開封でPCに挿さっているときはsleepが許され、コンソールを失う。
VBUSでロックする方針（上の「決めたこと」）はこの場合にも有効。

### 結果（2026-09-23）: 再現せず、運用で扱う

満充電・非充電中、画面OFFで測った。いずれもボタンでリセットし、1分以上置いてから読んだ。

| 版 | ポート | 電流 |
|---|---|---:|
| DFS（`cf58607` の計測ビルド） | 未開封 | 30.5mA |
| 同上 | DTR/RTSを下げて開く（`capture_serial.py`） | 31.0mA |
| 同上 | DTR/RTSを立てて開く（pyserial既定・`pio device monitor` と同じ） | 31.0mA |
| 作業7の通常ビルド（`53ee741`、240MHz固定） | 未開封 | 36.0mA |
| 同上 | DTR/RTSを下げて開く | 35.5mA |
| 同上 | DTR/RTSを立てて開く | 35.5mA |
| 同上 | 閉じたときのUSB経由リセット（`rst:0x15`）の後、未開封 | 32.0mA |

- **+16mAはどの条件でも再現しなかった**。作業7の版でも出ないので、DFSで消えたわけではない。
- `[UsbDiag]` では、ポートを開く前の約108秒間もSOFは途切れていなかった。**「ホストがバスを休止させていた」という仮説は否定された**。
- 開いた後、約24秒ごとに1秒程度SOFが途切れる記録があった。電流との関係は見えないので観察として残す。
- 作業7の日と今日の違い（PC側の状態、使ったモニタなど）は特定できていない。

対応: 原因の調査はここで打ち切る。**電流はボタンでリセットした後に読み、想定より高い値が出たらリセットして測り直し、そのときの条件を記録する**。
`[UsbDiag]` は計測ビルドに残し、再発時にSOFの状態を確かめられるようにする。
生ログは `20260923-usb-open*.log`。

同じ日の後半、`install-host` の読み出しが3回続けて失敗した（`Corrupt data, expected 0x1000 bytes but received 0xfff bytes`、
本体はROMのダウンロードモードで、ランチャーは動いていない）。ケーブルを挿し直すと成功した。
上記のSOFの途切れも同じ接続で記録しており、この日のUSB接続そのものが不安定だった可能性がある。
+16mAが再発したら、ケーブル・差し込み口を変えて再現するかも確かめる。

## 8-3. DFS

### 決めたこと

- `CONFIG_PM_ENABLE=y`。起動直後に `esp_pm_configure` で最大240MHz・最小80MHz、light sleepなしに設定する。
  最小を80MHz未満にしない。ESP32-S3のAPBは80MHz未満のCPUで下がり、
  パネル転送（QSPI）やI2Cのクロックが変わるため。
- **ランチャー独自のクロックロックは持たない**。IDFは、各コアがアイドルタスク以外を実行している間、
  `CPU_FREQ_MAX` のロック（`rtos0`/`rtos1`、`esp_pm/pm_impl.c`）を自動で保持する。
  80MHzへ下がるのは両コアがアイドルで待っている間だけで、**描画・入力処理・スロット走査は常に240MHzで動く**。
  したがってDFSは描画性能を変えず、待機中のクロックだけを下げる。
- 切り戻しは `-DLAUNCHER_CPU_MIN_MHZ=240` でビルドする。最小と最大が同じになり、作業7と同じ240MHz固定で動く。

当初は「操作中だけ240MHzを要求するロック」と、最大クロック未満で描いたフレームを数える集計を実装した。
実機で静止表示のフレームも240MHzで描かれていたことから上記のIDFの動作を確認し、
どちらも効果がないので取り除いた（2026-09-23）。

### 実機での確認

## 8-4. 入力のGPIO通知＋期限待機

### 目的

8-3までのランチャーは、画面OFF中も含めて10msごとに起きて入力を読んでいた（`M5.update()` はタッチのI2C読み出しを含む）。
待機中もCPUが毎秒100回240MHzへ戻るので、DFSの効果が削られる。これをやめ、入力の割り込みか次の期限まで眠る。
8-5のlight sleepもこの待機構造を前提にする。

### 決めたこと

- **ボタンか指が押されている間だけ10ms周期で読む**。直前の読み取りでA・B・タッチのどれかが押されていれば追跡中とし、
  リリース・A+B 600ms・ドラッグはこれまでどおり10ms周期で追う。押されていなければ入力の期限を持たない。
- 割り込みはMuteHidの `InputWake` を `src/hal/InputWake.cpp` へ移植した。KEY.A=GPIO2、KEY.B=GPIO1、タッチINT=GPIO13。
  Lowレベル割り込みで、ISRは自分のピンを無効化してUIタスクへ通知するだけ。待つ直前に、Highへ戻ったピンだけ再有効化する。
  Lowレベルを選んだのは、8-5のlight sleepからのGPIO起床がレベルしか扱えないため。
- 通知の有無はHALの `inputPending()` で `step()` が問い合わせ、通知があればその場で入力を読む。
  通知を `waitUs` の戻り値にしなかったのは、既存テストの多くが `wait()` を経ずに `step()` を呼ぶため。
  テスト用のHALは「何か押されている間は保留あり」を返し、Lowレベル割り込みを模擬する。
- スロット走査の作業者は、結果を出すたびにUIタスクへ通知する（`MultiFirmAdapter::publish`）。
  `poll()` はロックをブロッキングで取る（作業者の保持は1項目の書き込みだけ）。
- 割り込みの設定に失敗したら、HALが待ち時間を10msに制限し、従来のポーリングに戻る。
- USB状態の1秒周期は残す。静止・消灯中の起床は毎秒約1回になる。周期の見直しは8-5でVBUSロックと合わせて行う。
- M5Unifiedのボタンは、前回の更新から時間が空いていればデバウンスを飛ばし、最初の読み取りで押下を受け付ける
  （`Button_Class::setRawState` の `disable_db`）。長い待機の後でも押下を取りこぼさない。
- `m5stopwatch-measure` の60秒窓の行に、メインループの反復回数 `loops=` を加えた。

### PCでの確認

`tests/runtime_tests.cpp` を新しい待機に合わせて改めた。静止中の `wait()` が10msより長い、静止中は入力を読まない、
押下の通知でその場で読む、押している間は10ms周期、処理超過が続いても押している間は毎周期読む、を確かめる。

### 実機で見つかった問題と修正（2026-09-23）

**画面ON中のタッチがほとんど効かなくなった**（遷移・スクロールが10回に1回程度。消灯からのタッチ復帰とボタンは正常）。
M5GFXの `Touch_CST816S::getTouchRaw` は、直前の読み取りで触れていなかった場合、
10ms未満の再読み取りではINTがHighならI2Cを読まずに「触れていない」を返す。
タッチコントローラはINTを短いパルスで下げ、最初のパルスの時点ではまだ報告が読めないことがある。
割り込みのたびに即座に読むと、2回目以降は10ms未満・INTはHighに戻っており、読み取り自体が省かれていた。
消灯からの復帰は前回の読み取りから時間が空いているので影響を受けなかった。

修正: 割り込みの後100msは、触れていなくても入力周期（10ms）で読み続ける（MuteHidも最後の入力の後しばらく短周期で読む）。
追跡中の割り込みでは読み取りを前倒ししない。`tests/runtime_tests.cpp` の `interrupts()` で確かめる。

**ストップウォッチが40Hzから38.2〜39.5fpsへ落ちた**。次の更新期限を「描いた時刻＋25ms」で決めていたため、
期限まで眠って最大1tick遅れて起きる分が毎周期に加算されていた（以前は10msごとの入力確認が期限に間に合わせていた）。
修正: 期限そのものを起点に周期を刻み、1周期以上遅れたときだけ現在時刻から取り直す（遅れたフレームは追いかけない、全体計画6.2節）。
