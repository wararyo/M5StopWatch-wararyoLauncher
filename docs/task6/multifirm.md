# 作業6：MultiFirmホスト連携

## 現在の操作

起動すると先に時計が出て、その裏で `ota_1`〜`ota_3` の検証が始まります。検証が終わった順に
アプリ一覧の外部3行が更新され、起動できるスロットは自分の名前を名乗ります。

- **起動できるスロットは、一覧で決定するとそのまま起動します。確認画面は挟みません。**
  「起動中」が出てから約320msの再検証を経て再起動します。
- 起動できないスロット（検証中・空き・破損・読み取り失敗・非対応）は「外部アプリN」のまま、
  名前がグレーになります。一覧に状態の文字は出しません。
- そのグレーの行も開きます。開いた外部アプリ画面が、そのスロットが何なのかを説明します。
  スロット番号と、理由（検証中／空き／破損／読み取り失敗／非対応）とエラーコード、ボタンは「戻る」1つ。
- 「起動中」の間は、**A・B・タッチ・A+Bのホームを含めて一切の入力を受け付けません**。
  取り消せない区間だからです（[全体計画](../plan.md) 8.2節）。
- 起動に失敗すると理由を出して「戻る」が出ます。再起動はしません。
- ストップウォッチの行だけが、まだ「準備中」のトーストを出します（作業5）。

検証中のスロットを開いたまま走査が終わると、画面はReadyの表示（名前とバージョン）に変わります。
**そこでは起動しません。** 起動の契機は一覧での決定だけで、走査の完了は契機になりません。
起動できるスロットの省略前の名前とバージョンを読めるのは、実質この経路だけです。

ゲストからホストへ戻るのはゲスト側の責務です（A+B 1.6秒、MultiFirmの `return_gesture`）。
ホストの600ms規約をゲストへ適用しません。戻ってきたホストは必ず時計画面から始まります。

### 画面インターフェースを抽出しました

[作業4](../task4/settings.md) が「2つ目の実装が出た時点で抽出する」としていた `AppScreen` を、
外部アプリ詳細が2つ目になったこの作業で切り出しました。`SettingsScreen` も同じ基底に乗り、
`ScreenManager` は `ScreenId` ごとの分岐ではなく `AppScreen*` へ委譲します。
作業5のストップウォッチは3つ目の実装として乗るだけです。

表示モデルは画面ごとに型が違うのでインターフェースには入れません。`ScreenManager::model()` が
`SettingsModel` と `ExternalModel` を毎フレーム合成します（設定と同じく、どこにもキャッシュしません）。

### 走査はワーカー、起動はUIタスク

分け方の理由が非対称なので、ここだけ意図を残します。

**走査**（`inspectSlot` を1→2→3）は専用タスクです。1スロットあたりイメージ全体を2周読んで
SHA-256を計算するので時間がかかります。このランチャーの実測は**422/609/422ms・3本で約1.45秒**
（[作業6の検証記録](task6-validation.md)）。MultiFirmのphase3記録は別のゲスト構成で989msでした。UIタスクはCPU1に固定されている
（`CONFIG_ESP_MAIN_TASK_AFFINITY_CPU1`）ので、ワーカーはCPU0・優先度1・スタック8KiBで作り、
**1スロット終わるごとに**結果を公開して `vTaskDelay(1)` を挟み、CPU0のアイドルタスクへ実行機会を渡します。
`scanSlots()` ではなく `inspectSlot` ループなのは、結果を1件ずつUIへ返すためと、
`std::vector<SlotInfo>` を毎回確保しないためです。スタック8KiBはMultiFirmが
「4KiBのローカル配列でmainタスクのスタックが足りなくなった」記録を踏まえた値です。

**起動**（`bootSlot`）はUIタスクから同期で呼びます。`bootSlot` の shutdown コールバックは
**呼び出したタスクで**実行されるので、止める対象（表示、作業5以降は計測・音・振動）を持っている
UIタスクが唯一の正しい呼び出し元です。起動直前の再検証で約320msブロックしますが、
この区間は入力を抑止していて直後に再起動します。WDTのタイムアウト5秒に対して余裕があり、
**WDTの無効化やタイムアウト延長はしていません**（[全体計画](../plan.md) 6.2節）。

`AppRuntime` は「起動中」のフレームを**描画し終えてから** `commitPendingBoot()` を呼びます。
先に呼ぶと、画面が前のままフリーズしたように見えたまま再起動します。
`issued_` フラグがあるので、APIは1回しか呼ばれません。

確認画面を挟まないので、最終決定は一覧の決定そのものです。`ExternalAppScreen::enter()` が
カタログを見て、Readyならその場で `BootCommitting` に入ります。`enter()` の一度きりの判定なので、
画面を開いたあとにスロットがReadyへ変わっても起動は始まりません。

### 結果の受け渡し

ワーカーはミューテックスの下でカタログを書き、`generation` を1つ進めます。
UIタスクは `AppRuntime::step()` のたびに `poll()` し、世代が変わっていればコピーします。
入力ポーリングで最低10msごとにループが回るので、**この経路のために余分な起床は増えません**。
ミューテックスが取れなければ何もせず次の周回に回します（UIタスクは待ちません）。

`ScreenManager::setSlots()` がすることは一覧の行の更新だけです。画面を動かしませんし、
起動も始めません。だから**検証中にホームへ戻り、あとから結果が届いても無害**です
（[全体計画](../plan.md) 8.2節の最後の項目）。

### MultiFirm APIで気をつけたこと

- `inspectSlot` / `scanSlots` の**戻り値だけで成否を判定しない**。戻り値が非OKになるのは
  レイアウト不一致と不正indexのときだけで、個別スロットの失敗は `ESP_OK` ＋ `slot.state` で返ります。
  非OKのときはレイアウト側の異常として全スロットを「非対応」にし、走査を打ち切ります。
- `isMultiFirmLayout()` はフラッシュからパーティション表を読んでバイト完全一致を要求します。
  起動時に1回だけ評価して保持します。毎フレーム呼ぶ関数ではありません。
- `bootSlot` は `index` しか取りません。走査結果は信用されず、レイアウトもイメージも再検証されます。
  だからホスト側で「走査済みだから大丈夫」と省略する余地はありません。
- `partitions.csv` は1行も変えていません。バイト完全一致の検査があるので、
  コメント1つのズレでも全APIが `ESP_ERR_INVALID_STATE` になります。

### 描画

設定レイヤーと外部レイヤーは、**自分の画面が開いていないときは要素を1つも登録しません**。
画面の切り替えはもともと全面再描画（`Renderer::draw` の `m.screen!=previousScreen_`）なので
消し残しは出ません。同じ画面の中でのビュー切り替え（設定メニュー↔日時編集、詳細の位相変化）のための
空矩形登録はこれまでどおり残してあります。

これで同時に登録される要素は 時計5＋行5＋トースト1＋max(設定11, 外部6) = **22** で、
`FramePlan::Capacity=32` に収まります。両レイヤーを常時登録したままだと30になり、
作業5のレイヤーを足した時点で溢れます。

スロット名とバージョンはゲストのイメージから来る外部データなので、一覧の行名と同じく
`fitText` を通します。埋め込み部分集合にない文字は `?` になり、長すぎる名前は
文字単位で切り詰められます（[全体計画](../plan.md) 5.2節）。

## 実機確認手順

導入は[作業1のinstall-host手順](../task1/product-build.md)に従います。通常uploadは使いません。
`install-host` は16MiBバックアップの一致を確認したうえで `ota_0` だけを書き、ブートローダ・
パーティション表・ゲスト3スロット・NVS・otadata には触れません。

1. 通常版で起動。時計が先に出ること、そのあとで一覧の外部行が変わることを確認する。
   ログの `[MultiFirm] layout=valid`、`[Slots] layout=supported`、スロットごとの
   `[Slots] slot=N state=... name=... version=...` を記録する。
   MultiFirm側の `slot N image verification took ... ms` / `SHA-256 calculation took ... ms` も記録し、
   合計がphase3記録の約989msと同程度かを見る。
2. 走査中に一覧をスクロールし、描画が破綻しないこと、WDTが出ないことを確認する。
   走査中の描画時間を記録する。**この区間はフレームレートが体感で下がります**（下の注を参照）。
3. 起動できるスロットの名前が一覧に出ること、残りが「外部アプリN」のままグレーであることを確認する。
4. 起動できる行を決定し、**確認画面を挟まずに**「起動中」へ移ってゲストが立ち上がることを確認する。
   決定から起動までの時間を記録する。
5. ゲストでA+Bを1.6秒保持し、ホストが**時計画面で**起動することを確認する。
6. 空きスロットの行を開き、「空き」が出てボタンが「戻る」だけであることを確認する。
   検証中のスロットを開いたまま走査を終わらせ、Readyの表示へ変わっても**起動しない**ことを確認する。
7. 「起動中」の表示が出ている間に A・B・タッチ・A+B を入れても何も起きないことを確認する。
8. 描画検証版を導入し、`[Verify] ... result=PASS` / `mismatches=0` と
   `FAIL missing fixed UI glyph` が出ないことを確認する。
   この版は `FakeSlotService` を使うので、破損スロット・読み取り失敗・非対応レイアウト・起動失敗は
   ここで確認する。実機で本物の破損イメージやパーティション表の破壊は作らない。
9. 過負荷診断版で走査を含む60秒以上を操作し、`idf_cpu1` が正でWDT・再起動がないことを確認する。
10. 通常版へ戻し、`install-host` の前後でゲスト3スロットと設定（輝度・消灯時間・日時）が
    保持されていることを確認する。

結果は[作業6の検証記録](task6-validation.md)へ追記します。2026-09-22に全項目を確認済みです。

### 走査中はフレームレートが下がります

実機で確認した既知の挙動です。描画は破綻せず、WDTも出ず、走査が終われば元に戻ります。

`inspectSlot` はイメージ全体を512バイトずつ2周読むので、フラッシュ操作のたびにキャッシュが止まり、
CPU1のUIタスクもコードとPSRAMのフェッチで待たされます。ワーカーをCPU0へ逃がしても、
共有しているのはコアではなくフラッシュとキャッシュなので消えません。

窓は起動直後の約1.5秒だけで、その間ホームは静止した時計です。一覧を開くまで走査を遅らせると、
ジャンクがちょうどスクロール中へ移動して悪化するので、現在の配置のままにしています。
走査結果のキャッシュ（[全体計画](../plan.md) 8.1節が「実測後の改善候補」としているもの）を
入れれば2回目以降の起動で消せますが、初版の対象外です。

作業7の性能測定ではこの区間を別集計とし、操作中30fps超の判定には混ぜません。
