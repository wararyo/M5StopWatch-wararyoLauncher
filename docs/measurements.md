# 測定記録: 描画性能と消費電力

実機 M5StopWatch (ESP32-S3, 468x468 AMOLED, CO5300) での測定結果。

本書の前半は **測定用試作** の測定（2026-09-19〜20）で、値はそのまま保持する。
末尾の「製品版の測定」は **初版ファームウェア** の測定（2026-09-23、作業7）で、
前半とは版・構成・シナリオが違う。比較するときは必ず条件を合わせて読むこと。

## 測定環境

| 項目 | 値 |
|---|---|
| パネル | 468x468 RGB565、QSPI 80 MHz、M5GFX が PSRAM フレームバッファを自動構成 |
| CPU | ESP32-S3 240 MHz、PSRAM オクタル 80 MHz |
| ESP-IDF | 5.5.0 (PlatformIO espressif32 6.12.0) |

| 電源条件 | 満充電、全条件で `charging=0`、電池 4202〜4212 mV |

## 描画性能

### 最適化の経過

アプリ一覧のスクロール中の最悪フレーム時間の推移。

| 段階 | 最悪フレーム | 33 ms 超過 |
|---|---|---|
| 元の試作 (全画面スプライト) | 51.1 ms | 全フレーム |
| 中間スプライト廃止 | 27.7 ms | 0 |
| データキャッシュ 64 KB / 64 B ライン | 23.5 ms | 0 |
| 画面外カリング + 時刻テキストキャッシュ | 26.9 ms (ドラッグ実測) | 0 |
| 全画面クリア廃止 + 部分転送 | 25.6 ms (平均 13.6 ms) | 0 |

最後の 2 段階は最悪値だけ見ると横ばいだが、平均は大きく下がっている。
1 フレームを「クリア」「描画」「パネル転送」の 3 相に分けて計測すると
内訳が見える。いずれもアプリ一覧スクロール中の実測。

| 段階 | クリア | 描画 | 転送 | 合計 |
|---|---|---|---|---|
| スプライト廃止 + キャッシュ変更まで | 8.45 ms | 5.94 ms | 11.63 ms | 26.0 ms |
| 画面外カリング + 時刻テキストキャッシュ | 8.44 ms | 4.88 ms | 11.63 ms | 24.9 ms |
| 全画面クリア廃止 + 部分転送 | 0.006 ms | 7.85 ms | 5.25 ms | 13.1 ms |

最後の段階で描画相が増えているのは、消去処理が独立したクリア相から
描画相の中へ移ったため。純減で 11.8 ms 短縮している。

効いた順に。

- **中間スプライトの廃止が最大。** M5GFX は M5StopWatch で
  `Panel_AMOLED_Framebuffer` を組み込むため、`M5.Display` は最初から
  PSRAM 上のフルスクリーンバッファを持つ。そこへ 468x468x16bpp の
  スプライトを重ねていたので、1 フレームあたりの PSRAM 転送量が
  約 1.75 MB (クリア 437 KB 書き、pushSprite 437 KB 読み + 437 KB 書き、
  フラッシュ 437 KB 読み) になっていた。廃止して約 875 KB に半減。
- **部分再描画が次点。** フレームバッファは前フレームを保持したままにし、
  ボックスか内容が変わった要素だけが前回の矩形を消してから描き直す。
  パネル側のダーティ矩形追跡が触れた範囲だけを QSPI へ送る。
- **キャッシュ設定は小幅。** データキャッシュ 64 KB / 64 B ラインで
  最悪フレームが 27.7 ms から 23.5 ms へ。内蔵ヒープを 32 KB 消費する。

### 現在のフレームコスト

`RepaintCheck` の計測結果 (120 フレーム平均)。

| シナリオ | 平均 | 最悪 |
|---|---|---|
| アプリ一覧スクロール | 13.6 ms | 25.6 ms |
| 時計から一覧への遷移 | 12.1 ms | 17.3 ms |
| 時計の分更新 | 3.8 ms | 13.8 ms |
| 時計の静止 | 描画なし (120 回中 0 回) | - |

最悪値はスクロール位置が 188 から 0 へ折り返す合成動作によるもので、
実機のドラッグでは発生しない。

静止時に 1 フレームも描かないのが部分再描画の主な効果。ただし
`Renderer::draw` 自体は毎回 67 µs のレイアウト計算を行っており、
メインループ 100 Hz でデューティ比 0.7 % を消費している。

### 再描画の正しさ

部分再描画はフレームバッファを毎フレーム消さないため、結果が
それ以前の全フレームに依存する。目視では気付けない破綻が起きるので、
`measurement/src/ui/RepaintCheck.cpp` に自己検証を置いた。スクロールと遷移を
台本通りに動かしてからフレームバッファを読み戻し、同じ状態を
全面再描画した結果と 1 ピクセル単位で比較する。

この検証で実バグを 2 件捕まえた。

- **1 ピクセルの取りこぼし。** `fillCircle` は中心±半径を両端含めて
  塗るので高さは 2r+1。ボックスを 2r で計算していたため、スクロール時に
  アイコン最下行が消し残っていた。
- **レイヤーをまたぐ重なり。** 時計面とアプリ一覧は同一フレーム内では
  重ならないが、遷移の値が変わるとアプリ一覧の *前フレームの* 矩形が
  時計面の *新しい* 位置に重なる。その結果、一覧の消去が直前に描いた
  日付・時刻・ドットを削っていた。遷移 0.25 付近で画面上半分が消える。
  これが `FramePlan` で全要素の消去を描画より前に済ませる 2 段構成に
  した理由。

遷移値を 0.05 刻みで舐めた 24 パターンで不一致ゼロ。

有効化するには `measurement/platformio.ini` の `-DLAUNCHER_BENCH` を有効にする。

## 消費電力

### 測定方法

`measurement/src/power/PowerProfile.cpp` が台本通りに条件を切り替え、各条件を
120 秒保持してシリアルに開始と終了を出す。USB テスターの表示を
条件ごとに読む。ログは `docs/power-measurement.log`。

今回のテスターは mAh 積算が整数表示だったため、積算値の差分ではなく
**表示上最も頻繁に現れた mA 値を目視で採用**した。したがって各値の
確度はおおむね ±2 mA と見るべきで、それ未満の差は意味を持たない。

### 結果

| 条件 | 描画デューティ | 電流 | screen-off 比 |
|---|---|---|---|
| screen-off | 0 % | 38 mA | 0 |
| watch-idle (輝度 90) | 1 % | 38 mA | 0 |
| watch-forced-10fps | 23 % | 39 mA | +1 |
| watch-forced-20fps | 46 % | 39 mA | +1 |
| watch-forced-30fps | 70 % | 45 mA | +7 |
| list-scroll-max | 93 % | 55 mA | +17 |
| fill-black-30fps | 60 % | 37 mA | -1 |
| fill-white-30fps | 60 % | 62 mA | +24 |
| watch-idle 輝度 10 | 1 % | 39 mA | +1 |
| watch-idle 輝度 255 | 1 % | 45 mA | +7 |

### 読み取れること

**現在の時計画面は表示していても電力を消費していない。** screen-off と
watch-idle がどちらも 38 mA で、差が出ない。AMOLED なので黒は発光せず、
今の盤面はほぼ黒。パネルを消す意味が電力面ではほとんどないということ。

**支配的なのは表示内容であって再描画レートではない。** 全白は
+24 mA、時計盤は +0 mA。同じ 30 fps で全画面を描いていても、
黒 (37 mA) と白 (62 mA) で 25 mA 違う。盤面を黒基調に保つことが
最大の省電力策になる。

**輝度も内容次第。** 時計盤では輝度 90 と 255 の差が 7 mA しかない。
点灯ピクセルが少ないため、輝度を上げても代償が小さい。全白の盤面を
作ると同じ輝度差がはるかに大きく効くはず。

**最悪ケースでも 55 mA。** UserDemo の常時 80 mA と比べれば、
アイドル 38 mA / 最悪 55 mA は目標を満たしている。ただし下の
「読み取れないこと」を参照。

**残る改善余地は描画ではなく CPU とスリープにある。** screen-off が
38 mA あるということは、ベースラインが全体を支配している。この状態でも
CPU は 240 MHz のまま `vTaskDelay` で回っているだけで、light sleep には
入っていない。設計メモにある「将来は CPU クロックと light sleep も管理」が
次の打ち手になる。

### 読み取れないこと

**画面 OFF 時 20 mA の目標はこの方法では検証できない。** USB を挿している
限り USB PHY が動き続け、PMIC の充電回路も待機する。測定された 38 mA は
その分を含んだ上限値で、電池駆動での実際の消費はこれより低い。この目標の
確認には電池駆動での測定が必要。

**描画コストの傾きが取れていない。** デューティ 23 % と 46 % がどちらも
+1 mA、70 % で +7 mA と非線形になっている。さらに fill-black-30fps は
デューティ 60 % でありながら screen-off と同じ 37 mA。線形モデルでは
説明がつかない。原因の候補は測定分解能 (±2 mA の目視読み) と、
`fillScreen` の連続書き込みと描画要素の分散アクセスで PSRAM の
消費が違う可能性。現状は未解決。

**list-scroll-max は実機より重い。** 毎秒 70 フレーム描いている。
実機のドラッグはメインループの 16 ms 周期で毎秒 38 フレームが上限なので、
実使用の上限としては 55 mA より低いはず。

### 次に測るなら

- 電池駆動で screen-off と watch-idle を測り、USB 分を差し引く
- 積算 mAh が小数表示できるテスター、またはシャント + マルチメータで
  描画コストの傾きを取り直す
- light sleep と CPU クロック制御を入れた後のベースライン

PMIC (PM1, I2C 0x6E) に電流レジスタは **ない**。0x00 から 0x4F まで
全条件で読み比べたが、負荷で動くのは 16 bit リトルエンディアンの
電圧 3 つだけだった。

| レジスタ | 内容 |
|---|---|
| 0x20 | システムレール 約 3315 mV |
| 0x22 | 電池電圧 |
| 0x24 | VBUS 電圧 |
| 0x34, 0x36 | 500 固定。おそらく入力電流制限 mA |

他のバイトは画面 OFF でも全力描画でも完全に同一。本体から自己消費を
測る道はないので、外部計測が必須。

## ウォッチドッグの問題 (未修正)

`measurement/src/main.cpp:146` に問題がある。

```cpp
vTaskDelayUntil(&last, pdMS_TO_TICKS(dragging ? 16 : 10));
```

メインタスクは `CONFIG_ESP_MAIN_TASK_AFFINITY_CPU1` で CPU1 に固定
されている。`vTaskDelayUntil` は **期限をすでに過ぎている場合、
ブロックせずに即座に戻る**。フレーム時間が周期の 16 ms を超えると
期限が常に過去になり、CPU1 のアイドルタスクが一度も走らないまま
タスクウォッチドッグが発火する。

最適化前は以下が約 5 秒ごとに出ていた。

```
E (288506) task_wdt: Task watchdog got triggered.
E (288506) task_wdt:  - IDLE1 (CPU 1)
```

**現状は未確認。** フレーム時間が 13.6 ms まで下がって 16 ms 周期に
収まるようになったため、発火しなくなっている可能性が高い。ただし
実機のドラッグで確認していない。また最悪フレームは依然 16 ms を
超えるので、根本的には残っている。

修正案。

```cpp
if (!xTaskDelayUntil(&last, pdMS_TO_TICKS(dragging ? 16 : 10))) {
    last = xTaskGetTickCount();   // 期限超過時は基準を取り直す
    vTaskDelay(1);                // アイドルタスクへ最低 1 tick 譲る
}
```

`measurement/src/power/PowerProfile.cpp` の計測ループには同じ対策を入れてある。

## ハードウェア固有の注意

**命令キャッシュ 32 KB は起動しない。** `CONFIG_ESP32S3_INSTRUCTION_CACHE_32KB`
を有効にすると、約 6 秒ごとにリセットを繰り返し、コンソール出力が
一切出ない状態になる。2 段目ブートローダが最初の行を出す前に死んでいる。
Kconfig 上は何の制約もなく普通に選べるため警告も出ない。16 KB のみ動作する。

**フラッシュ QIO も起動しない。** `CONFIG_ESPTOOLPY_FLASHMODE_QIO` で
同じ症状。DIO のまま使う。

どちらも書き込み自体は esptool で普通に成功し、リセットループ中も
USB Serial JTAG は生きているので復旧は容易。

**PMIC は I2C 100 kHz でないと応答しない。** 400 kHz では全読み出しが
失敗する。さらに `M5.In_I2C.readRegister8()` は失敗時に黙って 0 を返す
ため、レジスタが全部ゼロに見えて誤読する。戻り値を確認できる
`readRegister()` を使うこと。32 バイトの一括読み出しも拒否されるので、
2 バイト単位で読む。

**`getVBUSVoltage()` は mV を返す。** 内部で V に変換してから 1000 倍
しているため、単位を V と誤解しやすい。

## 再現方法

`measurement/platformio.ini` の `build_flags` で切り替える。どちらも既定では無効。

| フラグ | 内容 | 所要 |
|---|---|---|
| `-DLAUNCHER_BENCH` | 部分再描画の自己検証とフレームコスト計測 | 約 30 秒 |
| `-DLAUNCHER_POWER_PROFILE` | 消費電力の台本計測 | 約 21 分 |

どちらも起動時に自動で走り、シリアルへ結果を出す。電力計測は
事前に満充電にすること。充電中はテスターが充電器を見ているだけで、
本体の消費は読めない。各条件の `charging=1` はその条件が無効という印。

ビルドフラグを変更した直後の 1 回目のビルドは
`Couldn't find target config` で失敗する。もう一度実行すれば通る。

## 製品版の測定 (作業7、2026-09-23)

試作ではなく初版ファームウェアの測定。試作の値は上の節に残してあり、置き換えていない。
詳細な経緯と分析は [作業7の詳細計画](task7/plan.md) の 7-2〜7-4、生ログは `task7/20260923-*.log`。

### 測定環境

| 項目 | 値 |
|---|---|
| ファームウェア | `wararyoLauncher` 0.1.0-dev、ESP-IDF 5.5.0、M5Unified 0.2.16 / M5GFX 0.2.28 |
| 描画測定のビルド | `m5stopwatch-measure`（製品構成＋`[RenderDiag]` の集計のみ） |
| 電力測定のビルド | `m5stopwatch`（通常ビルド、SHA-256 `b6eeba13…`） |
| 機体 | MAC 28:84:85:43:a7:c0、MultiFirm v1、ゲスト3スロット実装済み |
| 設定 | 輝度105、消灯15〜180秒、CPU 240MHz固定、PM・light sleepなし |
| 電流計 | USBテスター目視、確度約±2mA。満充電・非充電中 |

### 描画性能

60秒窓を区間ごとに集計した値。`-cont` は200ms超の休止を除いた連続区間。

| 区間 | 描画時間 平均 / 最大 | 連続区間の実fps | 描画の33.3ms超過 |
|---|---:|---:|---:|
| ストップウォッチ実行中 (25ms周期) | 1,818us / 4,689us | 39.98〜40.00 | 0 / 5,676 |
| 時計↔一覧の遷移 | 15,763〜16,288us / 30,895us | 35.06〜37.15 | 0 / 2,720 |
| 一覧スクロール | 30,104〜30,435us / 35,510us | 28.73〜29.83 | 446〜497 / 1,700〜1,747 |
| 入力→表示 | 平均31,208us / 最大37,704us | — | 目標100ms以内 |
| 消灯→復帰 | 平均24,947us | — | 目標300ms以内 |
| 静止（時計） | 描画なし | 0fps | 60秒窓で `paints=1` |

**一覧スクロールだけが6.3節の「操作中30fps超」に届いていない。** 休止は3窓中2窓で0件なので、
操作停止時間では説明できない。同じく変更領域がほぼ全画面になる遷移が16msで収まっているため、
全画面転送だけでも説明できない。内訳（plan / paint / 転送）は未測定。

起動直後のスロット走査は3スロットで3.17秒。走査を含む窓には最大127msの単発フレームが出るが、
同じ窓のスクロール描画平均は走査後の窓と変わらない。

メモリは全窓で一定（内部RAM空き 240,167〜247,339、最大連続 192,512、PSRAM空き 7,939,612、
スタック余裕 4,900 bytes）。65分の連続動作でも `247,207` から動かない。

### 消費電力

**シリアルポートを開いていない状態**の値。開いていると全条件に +16mA 以上が乗る（下記）。

| 条件 | 電流 | 電力 | 目標との関係 |
|---|---:|---:|---|
| 時計静止・画面ON | 36.0mA | 0.1854W | アイドル40mA目標は達成 |
| 一覧を連続スクロール | 55.0mA | 0.2854W | 試作の55mAと一致 |
| 画面OFF・計測なし | 35.5mA | 0.1828W | **画面OFF 20mA目標は未達** |
| 画面OFF・計測中 | 35.5mA | 0.1828W | 計測の電力コストは検出できず |
| 画面OFF（USB充電器、データ接続なし） | 35.5mA | 0.1803W | 給電元では変わらない |

画面ONと画面OFFの差は0.5mA、計測中と計測なしの差は0mA。試作と同じく、
**表示と計測の差はこの精度では検出できない**。

### 罠: シリアルポートを開くと消費が上がり、閉じても戻らない

同じ条件で16mA以上ずれる現象があり、切り分けると **ホストがUSB Serial JTAGのCDCポートを
開いたかどうか** で決まっていた。ケーブルがPCに挿さっているだけでは上がらない。

| 条件 | リセット後・ポート未開封 | シリアル接続後 | 差 |
|---|---:|---:|---:|
| 時計静止・画面ON | 36.0mA | 52.5mA | +16.5 |
| 一覧を連続スクロール | 55.0mA | 72.5mA | +17.5 |
| 画面OFF・計測なし | 35.5mA | 51.5mA | +16.0 |
| 画面OFF・計測中 | 35.5mA | 51.5mA | +16.0 |

全条件へ一律に乗るので負荷とは無関係。ポートを閉じても戻らず、リセットするまで続く。
**電力を測るときはシリアルを開かない。開いてしまったらリセットしてから測り直す。**

2026-09-23（作業8-2）に同じ手順で再現を試みたが、作業7の版でも、DTR/RTSの状態を変えても +16mA は出なかった。
原因は特定できていない。上の注意は運用として残す。詳細は [作業8の詳細計画](task8/plan.md) の8-2。

### もう1つの罠: キャプチャの終了が本体をリセットする

`tools/capture_serial.py` の初版は、pyserialがポートを開くときDTR/RTSをアサートし、
閉じるときにドライバがそれを落とすのをそのままにしていた。この板ではその組み合わせが
リセット手順で、`rst:0x15 (USB_UART_CHIP_RESET)` が起きる。**記録を止めた後**に起きるので
ログには何も残らず、1時間の長時間計測が経過時間を読む前に再起動していた。
現在はリセットを頼まれていないとき、開く前にDTR/RTSを下げてから開く。

### 再現方法

```powershell
pio run -e m5stopwatch-measure
# MultiFirm の install-host で ota_0 だけを更新する（docs/task1/product-build.md）
python tools/capture_serial.py COM11 150 docs/task7/<シナリオ>.log
```

1シナリオにつき150秒記録し、60秒窓を2〜3本取る。窓は自動で出るので、
